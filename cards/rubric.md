# 평가 기준 지도

정확한 배점은 공개되지 않았어요. 아래는 주최 측 기사와 공식 응시 가이드에서 확인된 것, 그리고 비공식 정보를 구분해서 정리한 거예요.

## 1. 공식으로 확인된 것

### 평가 3축
| 축 | 공식 설명 |
|---|---|
| Technique (기술 관리) | 코드의 실행성과 구조, 보안 |
| Intent (의도 관리) | AI에 목표와 제약을 정확하게 전달했는지 |
| Cognition (인지 관리) | AI 결과를 직접 검증·수정했는지, 결과의 작동 원리와 실패 가능성을 설명할 수 있는지 |

### 세부 항목 (기사 원문)
"코드의 실행성과 구조·보안에 더해 **문제 정의와 우선순위 설정, AI에 대한 지시 품질, 근거 탐색과 의사결정, 반복 개선과 오류 복구, 결과 검증 능력**을 함께 본다."
평가하는 과정: 문제 정의 → AI에 대한 역할 배분과 지시 → 근거 탐색 → 판단 수정 → 오류 복구 → 결과 검증.

### 채점 방식
- 역량별 평가 기준에 따라 **AI 평가 에이전트가 자동 평가**하고 면접 참고 리포트를 만들어요.
- 평가 에이전트를 반복 시험·개선하는 **메타 하네스**로 "같은 제출물엔 같은 점수, 다른 제출물은 확실히 구분"되게 만들었대요.

### 수집되는 기록 (공식 가이드)
- 내장 AI·코딩 에이전트(Codex)·업무 담당자와의 **대화**
- 터미널 CLI 세션, **AI 도구 설정** (AGENTS.md, skill, agent, MCP)
- **git 로그·diff, 테스트 실행 결과**
- 코드, 계획 문서, 협업 기록 등 작업 공간의 결과물 파일
- 확인 문제 답변 (제출물과 작업 기록을 바탕으로 문항 생성)

### 그 밖의 공식 기준
- **토큰 사용량은 추적되고 간접적으로 평가에 쓰일 수 있어요.**
- **에이전트 응답시간을 고려한 위임과 시간 안배도 AI 활용 역량으로 봐요.**
- 제출 문서는 AI와 함께 써도 불이익이 없어요. **판단과 근거, 검증 결과, 남은 한계**가 담겼는지를 봐요.
- 확인 문제는 질문 전제가 실제 구현과 다르면 그 차이를 밝히고 내 작업을 설명해요.

## 2. 비공식 정보 (참고만)
- 다른 참가자 자료: "20여 개의 평가 에이전트가 DM, 프롬프트와 토큰 효율, 도구 설정, 실행 기록, git, 제출 문서, 확인 문제 답변의 **일관성을 교차 채점**한다." 출처 미확인. 다만 공식 수집 목록과 맞아요.
- 같은 자료에 인용된 설계자 발언: "전체 설계와 핵심 논의는 주도적으로 하고, 단순 구현과 실행은 서브 에이전트로 분리해 위임하는 오케스트레이션." 출처 미확인.
- 이전 대회 후기: 참가자 전원이 **Cognition 점수가 가장 낮았고**, 상위권은 handoff skill로 좋은 평가를 받았대요.

## 3. AI 채점관이 보는 증거와 우리 장치
| 항목 | 채점관이 볼 증거 | 우리 장치 |
|---|---|---|
| 실행성 | 실행 명령과 테스트가 실제로 돌아간 로그 | wb-verify, audit `--run-tests` |
| 구조·보안 | diff, 비밀값, 입력 검증 | wb-worker 규칙, wb-reviewer, audit |
| 문제 정의 | DM 질문의 질, 요구사항의 출처, 합의 확인 | wb-kickoff, DM_LOG, REQUIREMENTS |
| 우선순위 | Must/Should/Could, Must를 먼저 완성했는지 | REQUIREMENTS, slice 계획 |
| 지시 품질 | 프롬프트와 스펙에 목표·제약·완료 기준·범위가 있는지 | 프롬프트 카드(내 말로), specs |
| 역할 배분 | 위임 기록과 지시 내용 | sub-agent spawn 기록, trace |
| 근거·의사결정 | 결정마다 근거와 대안 | NOTES 결정 4줄, explorer |
| 개선·오류 복구 | 판단 변경, 원인 분석, 재검증 | NOTES 판단 변경·오류 복구 |
| 결과 검증 | 실행된 검증, 엣지 케이스, 데이터 검산 | R-id 테스트, 검증 기록 |
| 설명 능력 | 보고서의 한계·실패 조건, 확인 문제 답변 | REPORT, wb-examiner, 확인 문제 카드 |
| 효율 | 토큰, 반복, 시간 안배 | 빈 맥락 sub-agent, 역할별 effort, handoff |
| 일관성 | 기록끼리 서로 맞는지 | R-id 연결, wb-grader의 X1 |

## 5. 감점 패턴 (평가 에이전트가 "나쁜 예"로 학습했을 가능성이 높은 것)
- "다 만들어줘" 한 방 프롬프트. 목표·제약·완료 기준이 없는 지시
- AI 결과를 그대로 수용 (검증·수정·거부 기록 없음)
- 에러를 무시하거나 테스트를 약하게 고쳐서 통과
- 요구사항 확인 없이 바로 코딩, README에 있는 걸 DM으로 다시 묻기
- 설정만 화려하고 실제로 안 쓴 도구 (설정과 사용 기록이 안 맞음)
- 문서와 로그가 서로 다른 말을 함 (실행 안 한 검증을 했다고 씀)
- 같은 요청 반복, 거대한 파일·로그를 통째로 출력 (토큰 낭비)

## 6. AI가 도는 동안 내가 할 일 (대기 시간 = 낭비 + 비활성 일시정지 위험)
- DM 추가 질문, DM_LOG 정리
- 직전 slice의 diff를 직접 읽고, 결정과 이유를 내 말로 NOTES에 적기
- 다음 스펙에 넣을 조건 정리
- 핵심 코드를 읽어 두기 (확인 문제 대비)
- 표본 몇 건을 직접 검산하기 (`python3 .kit/tools/sample.py <파일>` 출력)

## 7. 주의
- **실행하지 않은 걸 했다고 쓰면 안 돼요.** 채점관은 터미널과 테스트 로그를 같이 봐요. 증거가 없으면 실제로 돌리고 나서 기록해요.
- **문서보다 결과물이 먼저예요.** 안 돌아가는 코드를 좋은 문서로 덮을 수는 없어요.
- 모의 채점은 추정이에요. 실제 배점과 다를 수 있어요.
