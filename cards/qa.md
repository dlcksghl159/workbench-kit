# 확인 문제 카드 (외워서 들어가기)

## 진행 (공식 가이드)
1. "제출하고 문제풀기" → 미리보기 → "제출물 확정하고 문제풀기". **확정하면 파일을 더 고칠 수 없어요.**
2. 문제 준비 대기: 최대 10분. 자동 재시도하면 대기가 다시 시작돼요. 이 시간은 답변 타이머가 아니에요.
3. 문항 수 확인 (응시 화면 기준, 안내상 6문항) → "문제 풀기"를 누르면 1번 타이머 시작.
4. 문항당 5분. **다음 문항 타이머는 직전 답안을 제출하는 순간 바로 시작돼요.** 쉬는 시간이 없어요.
5. 시간이 끝나면 지금까지 쓴 답이 자동 확정돼요. 그러니 핵심 문장부터 먼저 써 두세요.
6. AI, 외부 창, 복사·붙여넣기, 이전 문항으로 돌아가기 모두 불가. 직접 타이핑해요.
7. 마지막은 "답안 제출하고 마치기" → 완료 화면에서 제출 ID·시각·파일 수 확인.

## 실제 문제 모양
- 화면 제목은 "제출 전 이해도 확인"이에요. 한 문제가 길고, 하위 질문 3~5개가 쉼표로 묶여 있어요.
- **제출물을 읽고 만들어요.** 내 코드의 구현 세부를 그대로 인용하고, 제출 문서를 파일명과 내부 ID까지 짚어요. 예: "협업 문서의 [ID] 항목 중 '[작업 이름]'을 실제로 어떻게 진행했나요?"
- 그래서 문서에 ID를 붙여 쓴 항목은 전부 문제 재료예요. 내가 설명하지 못하는 항목은 문서에 넣지 않아요.
- 빈 답은 제출되지 않는 것으로 보여요. 한 줄이라도 써요.

## 4유형과 답 틀

### 1. 설계 선택
묻는 것: 어떤 방식으로 풀었나 / 기본안 위에 어떤 개선 단계를 얹었나 / 최적해 대신 왜 이 방식인가 / 다른 접근과의 차이 / 감수한 한계
1. 방식 한 줄: "기본안은 [단순한 방법]이고, 그 위에 [개선 1] → [개선 2]를 얹었습니다."
2. 단계마다 목적과 수치: "[개선 1]로 [지표]가 [a → b]가 됐습니다." 재료는 NOTES의 설계 기록이에요.
3. 최적·정확한 방법을 안 쓴 이유: 응답 시간, 문제 크기, 새 의존성, 설명하고 재현할 수 있어야 한다는 점, 시간 안에 검증까지 끝낼 수 있는 범위.
4. 다른 접근과의 차이: 버린 대안 1~2개와 버린 이유.
5. 한계와 보완: 국소 최적, 입력 순서에 따라 결과가 달라짐, 설정을 바꿨을 때 결과가 한 방향으로 움직인다는 보장이 없음 → 어떤 검사로 보완했는지.

### 2. 구조
묻는 것: 어떤 모듈이 어떤 책임을 갖나 / 데이터와 상태가 어디에 저장되나 / 입력부터 각 화면까지 어떻게 흐르나
1. 진입점 한 줄 (서버, 라우트, 명령).
2. 모듈 3~5개, 파일명과 책임 한 줄씩.
3. 상태마다 저장 위치: 파일, DB, 메모리. 재시작하면 남는지.
4. 요청 하나를 끝까지 따라가기: 입력 → 검증 → 저장 → 처리 → 화면마다 조회.
5. 입력 검증과 권한 구분이 어디서 일어나는지.

QA_DRILL의 B(구조 지도)를 외워 가요.

### 3. 변경 검증
묻는 것: 사용자가 설정을 바꿔 다시 돌렸는데 결과가 이상하다면 무엇으로 확인하나 / AI 결과에서 어디를 믿지 않고 더 검증하나
1. **기대 방향부터 말해요.** 한도나 용량을 늘리면(제약을 풀면) 결과가 나빠지면 안 되고, 조이면 좋아지면 안 돼요. 정확한 방법이면 보장되지만 휴리스틱은 보장이 없어요. 이전 결과가 새 설정에서도 유효하다면, 새 결과가 더 나쁠 때 이전 결과를 유지하는 장치로 막을 수 있어요.
2. 확인 근거는 이 순서로 봐요.
   1. 바꾼 값이 실제로 쓰였나: 저장된 결과에 남은 설정 기록.
   2. 항상 지켜야 할 조건: 한도 초과 0건, 모든 입력이 처리됐거나 사유가 남았나, 마감 시각을 지켰나.
   3. 이전 결과와 비교: 개수, 합계, 가장 나쁜 개인 사례.
   4. 손으로 계산할 수 있는 작은 사례로 재현.
   5. 같은 입력으로 두 번 돌려 같은 결과인지.
3. AI를 믿지 않을 곳: 테스트 기대값을 AI가 같은 코드로 계산해 넣은 경우(순환 검증), 시간 단위와 반올림, 거리나 시간 계산의 가정, 이전 결과나 캐시가 그대로 쓰였는지, 경계값(한도와 같은 값, 0).

### 4. 과정 서술
묻는 것: 문서의 [ID] 항목을 실제로 어떻게 진행했나 / 어떤 문제를 어떻게 발견했나 / AI에게 무엇을 요청했나 / AI의 수정과 검증 중 받아들인 것·고친 것·버린 것 / 각각의 판단 근거 (실행한 검사와 결과)

답 틀: "[검사·관찰]에서 [수치]를 보고 [문제]를 발견했습니다. AI에게 '[요청 요지]'를 요청했습니다. AI가 [A, B, C]를 냈고, A는 [명령 → 결과]로 확인해 받아들였고, B는 [이유]로 고쳤고, C는 [이유]로 버렸습니다. 최종 [재검증 명령 → 결과]로 확인했습니다."

재료는 NOTES의 'AI 결과 판정'(J-id)이에요. 작업 중에 판정 한 줄을 내가 직접 말해 둬야 5분 안에 쓸 수 있어요 ([P3.5](prompts.md)).

## 쓰는 공식: 하위 질문마다 한 문장
1. 30초: 질문을 쉼표 기준으로 쪼개 하위 질문 개수를 세요.
2. 첫 문장은 결론이에요. 그다음 하위 질문 순서대로 한 문장씩, 질문의 단어를 문장 앞에 그대로 써요. 예: "개선 단계는 …", "최적해 대신 이 방식을 고른 이유는 …", "감수한 한계는 …".
3. 문장마다 근거 하나를 넣어요: 파일명이나 함수명, 명령과 결과, 수치, J-id.
4. 남은 시간에 수치를 채워요. 모르면 추측하지 말고 "확인하지 못했습니다. [명령]으로 확인하겠습니다."라고 써요.

## 질문 전제가 실제 구현과 다를 때 (가이드 공식 안내)
첫 문장: "질문의 전제와 실제 구현이 다릅니다. 실제로는 ~하도록 구현했습니다." 그다음 하위 질문 순서대로 써요.

## 꼭 나올 수 있는 질문: AI를 어떻게 썼나요?
1. "요구사항 정의와 판단은 제가 하고, Codex는 탐색·구현·리뷰·모의 채점 역할로 나눠 썼습니다."
2. "요구사항마다 R-id를 붙여 스펙, 테스트, 커밋, 보고서까지 연결했고, 위임할 때는 스펙 파일 하나만 넘겼습니다."
3. "AI 결과마다 받아들일지, 고칠지, 버릴지를 제가 판정하고 근거가 된 검사를 기록했습니다. 예를 들어 [J-id 사례]는 [검사 결과]를 보고 [고쳤습니다/버렸습니다]."
4. "한계는 [시간 때문에 못 한 것]이고, 더 있었다면 [다음 검증]을 했을 겁니다."
